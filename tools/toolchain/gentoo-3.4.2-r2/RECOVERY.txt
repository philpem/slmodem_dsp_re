  Gentoo's CVS history is reachable ONLY over the git protocol today:
  gitweb.gentoo.org/archive/... returns HTTP 502, and sources.gentoo.org (the
  old ViewVC) is dead and 301-redirects into that same 502. The way through:
      git clone --filter=blob:none --bare \
          https://anongit.gentoo.org/git/archive/repo/gentoo-2.git
      git show 789964eafd96:sys-devel/gcc/files/digest-gcc-3.4.2-r2
  This yields all six md5s + sizes. It also holds the ebuild and eclass.

  get_gcc_src_uri(). This is what revealed dev.gentoo.org/~lv/GCC/ (a path that

  www.research.ibm.com/trl/... as distinct from www.trl.ibm.com/...

WHY NO OFFICIAL MIRROR HAD THEM
  Official Gentoo mirrors run rsync --delete, so they are mirrors, not archives;
  once Gentoo pruned these files they vanished everywhere downstream. Verified:
  all 284 current HTTP mirrors re-probed at the CORRECT sharded paths (852
  probes) -- zero hits; 159 hosts from the 2005-era mirror list -- zero; and
  releases/{x86,amd64}/ today contain only autobuilds/ and binpackages/.
  Surviving copies are all on individuals' personal web space.

  IMPORTANT if you ever re-run a mirror sweep: Gentoo mirrors are NOT flat.
  https://distfiles.gentoo.org/distfiles/layout.conf says
      [structure]
      0=filename-hash BLAKE2B 8
  so files live at  distfiles/<2-hex>/<filename>  where the 2 hex digits are the
  first 8 bits of BLAKE2B of the FILENAME (computable without the file):
      1e  gcc-3.4.2-patches-1.1.tar.bz2
      29  gcc-3.4.0-piepatches-v8.7.6.5.tar.bz2
      d3  protector-3.4.1-1.tar.gz
  A flat probe 404s whether or not the file is present. Always run a positive
  control (a file known to exist) before believing a 404, and a negative control
  (an impossible filename) before believing a 200 -- several hosts
  (mirror.meowsmp.net, gentoo.mirrored.ca, www.tek.net, live www.trl.ibm.com)
  return 200 + HTML for any name, and FTP mirrors return 221 for garbage names.

CAVEAT: bloodnoc.org is one person's web directory and could disappear at any
time. This local set is now the safe copy -- keep a backup.

WHY THE .comment STRING HAS A DOUBLE SPACE -- and why this proves the recipe:
  release_version = "Gentoo Linux ${PVR}"            -> "Gentoo Linux 3.4.2-r2"
                  + ", ssp-${PP_FVER}"               -> ", ssp-3.4.1-1"
                  + ", pie-${PIE_VER}"               -> ", pie-8.7.6.5"
  BRANCH_UPDATE is EMPTY for this ebuild, so the argument passed is
      " (Gentoo Linux 3.4.2-r2, ssp-3.4.1-1, pie-8.7.6.5)"   [leading space]
  gcc_version_patch() then seds gcc/version.c:
      s~\(const char version_string\[\] = ".....\).*\(".*\)~\1 @GENTOO@\2~
  \1 captures `"3.4.2`, and the replacement re-emits it followed by a SPACE and
  then @GENTOO@ -- which itself begins with a space. Hence:
      3.4.2 + " " + " (Gentoo Linux 3.4.2-r2, ssp-3.4.1-1, pie-8.7.6.5)"
    = "GCC: (GNU) 3.4.2  (Gentoo Linux 3.4.2-r2, ssp-3.4.1-1, pie-8.7.6.5)"
  The anomalous double space falls out of the recipe. That is independent
  confirmation -- separate from the MD5s -- that this ebuild+eclass pair is
  exactly the one that built the object under study.

Verifying you rebuilt the right thing -- compile anything and check:
