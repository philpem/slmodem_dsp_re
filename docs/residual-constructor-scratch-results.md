## Jd's byte capture is not the first clone difference

The independently identified Jd C1/C2 patterns agree through27.flow2, including
lookahead pseudo60 allocated in AX in both. Their sole scratch searches belong
to immediate-zero store UID30: C2 enters0, selectsDX, exits2; C1 enters2,
selectsBX, exits13. Peephole2 differs at UIDs263/264; renaming then creates nine
differing patterns and moves C2's lookahead to BX while C1 keeps AX. The final
lookahead colour does not diagnose different source capture or early allocation.
Both C1 and exact C2 retain the existing captured byte and source age.

The opening domain incorrectly described the lookahead difference as already
occurring at allocation, based on comparing our allocated register with the
original's final register. That is not a valid stage comparison. Preserve the
opening text under build/residual-constructor-scratch/domain-opening.md and
correct the domain after the explicit clone-to-clone observation. No source
candidate or invalid compilation resulted from that mistaken premise.

Parameters C2/C1 each make two searches, identified dynamically by assembler

## Compiler heap addresses are not constant values

Two apparent early C2 differences were <string_cst> compiler heap addresses
inside the same *.LC23/*.LC25 symbol references. The audit removes only this
explicit annotation address, keeping symbol identity and all real immediates.
Three controls prove annotation-only differences disappear, changed pool symbol
identity remains a difference, and a changed real constant remains a difference.
After that limited correction, all pre-peephole C2 instruction patterns agree.
No relocation bytes, source values or tree structure are erased.
