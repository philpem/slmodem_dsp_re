# Known-callee alignment diagnostic

This is compiler apparatus, not reconstruction source or a production source/flag experiment. Run `python3 tools/gcc3_alignment_micro.py` from this worktree. It reads `build/production-before/.build-config`, uses its complete C++ profile and appends `DSPLIB_REPRODUCE_BUGS`, then records driver commands, selected assembler execution, preprocessed input, raw assembly, objects and read-only GDB observations under `build/gcc3-alignment-micro`.

The tool extracts the installed cc1plus from the recorded published Gentoo image; its SHA256 is recorded. The observer is a prefix-limited adaptation of the merged Uref observer. It reads compiler memory, sets observation breakpoints and follows returns; it neither calls inferior functions nor changes compiler state. Driver assembly, standalone installed-cc1plus assembly, and observed assembly must agree byte for byte. Reassembled observed objects must equal driver objects.

Eight small TUs cross callee definition before/after caller with four callee mechanisms. Every TU has two exported definitions; `noinline`, `volatile` and explicit alignment are diagnostic controls only. No production definition is moved.

| Callee body | Local alignment needed | Published incoming boundary | Caller allocation |
|---|---:|---:|---:|
| Integer leaf | 4 bytes | 4 bytes | 4 bytes |
| Volatile double slot and conversion | 8 bytes | 4 bytes | 4 bytes |
| Same slot explicitly aligned(8) | 8 bytes | 4 bytes | 4 bytes |
| External-call wrapper | 4 bytes | 16 bytes | 8 bytes |

The leaf caller pushes EBX then allocates four bytes; the library-wrapper caller pushes EBX then allocates eight. Their outgoing argument payload is one four-byte integer. The double callee allocates 20 bytes, but its incoming boundary remains four bytes. Therefore local slot alignment and published incoming alignment are distinct measurements. A double slot is a refusal control for the tempting inference that an eight-byte local forces an eight-byte requirement on the caller. Even explicit local aligned(8) does not establish that transfer in this profile. These controls do not demonstrate an intermediate eight-byte published boundary.

All four definition-order pairs emit raw-identical objects. In all eight TUs, an early `cgraph_rtl_info` query sees `asm_written=0` and returns NULL; a later caller query sees `asm_written=1` and returns the recorded 32- or 128-bit requirement. In both external-call TUs, queries for the undeclared-body external function remain NULL. Thus the detector fires on known compiled callees and refuses missing RTL information; it is not merely reporting every callee as known.

GCC 3.4.2 source explains the observations. In recovered `cgraph.c:349`, `cgraph_rtl_info` returns NULL when a noncurrent function has not been written to assembly. In `calls.c:2347–2352`, call expansion starts with `PREFERRED_STACK_BOUNDARY`, replacing it only when callee RTL information exists and contains a nonzero `preferred_incoming_stack_boundary`. The official GCC3.4.2 sources corroborate these installed-binary observations; see the linked sources in [the prior Uref report](gcc3-uref-stack-results.md). Under the retained unit-at-a-time pipeline, source order does not imply emission availability: both orders eventually compile the dependency before caller expansion. No experiment changed unit-at-a-time or other flags.

Denominators: eight valid TUs, two defined functions each, eight unchanged observer replays, four unchanged source-order object pairs, eight early-unwritten refusal controls, and two external-unknown refusal controls. Full traces and complete commands are in `results.json`; frame-layout observations include callee and caller separately. Runtime, value equivalence and whole-production byte-exactness were not measured here. No source/header, central finding, issue or production object was changed.

The useful next discriminator is an observed real caller's callee availability and published boundary, not a definition-order permutation or guessed double-width requirement. A changed real callee call graph could propagate sixteen-byte alignment transitively; a callee without library calls can publish four-byte alignment despite eight-byte slots. Capture actual callee RTL publication and the caller's selected boundary before attributing a frame difference to this mechanism. A truly eight-byte incoming boundary would need a separately observed producer; this diagnostic gives no evidence to manufacture one from local slot width.

## Written weak/template callee extension

Three additional TUs retain the same profile and caller: weak leaf defined before/after caller, and one explicitly instantiated noinline template leaf. Together with the previous eight, eleven valid TUs each contain two measured defined functions. All eleven raw compiler/observer output replays pass. The fifth definition-order pair (weak) is raw-identical. The template emits a weak symbol in `.gnu.linkonce.t._Z14align_templateIiEiT_`; its compiler `weak_flag` is one and `comdat_flag` is zero. Do not confuse the literal compiler COMDAT flag with the presence of a linkonce ELF section.

For the strong leaf, installed `default_binds_local_p_1` returns true, and the later caller query sees `asm_written=1` with published boundary 32 bits. For the two weak and one template controls, this function returns false with `shlib=0`; later queries still see `asm_written=1` but boundary **zero**, and caller preferred alignment remains 128 bits. All three callers allocate eight bytes after pushing EBX, compared with four for the strong leaf. These are written-negative publication controls, distinct from the eleven early unwritten-query refusals and two external-unknown refusals. All original eight controls still reproduce their earlier result.

The recovered GCC 3.4.2 `toplev.c:3675–3682` publishes `preferred_incoming_stack_boundary` only when `targetm.binds_local_p(current_function_decl)` succeeds. It publishes `cfun->preferred_stack_boundary`, except that a recursive emitted call can raise it to `stack_alignment_needed`. This explains why an ordinary nonrecursive eight-byte local need did not publish eight-byte incoming alignment. Official GCC 3.4.2 `varasm.c:5143–5180` implements `default_binds_local_p_1`: default-visible external, linkonce/weak, and shared-library declarations do not bind locally; earlier private or nondefault-visibility cases can bind locally. Source downloaded from [GCC releases/gcc-3.4.2](https://raw.githubusercontent.com/gcc-mirror/gcc/releases/gcc-3.4.2/gcc/varasm.c) is saved under the diagnostic artifacts. Installed function returns corroborate these source rules; no inferior function invocation was used to obtain them.

This supplies a concrete reason for a compiled template callee's zero published boundary. Applicability to any real callee still requires its actual declaration/binding and observed publication; availability alone is insufficient. A real frame reduction accompanying zero boundary in every cell cannot be credited to this transfer mechanism. Saved-register count and frame-layout components must be examined independently. No production binding, visibility, attributes, or source order should be changed to imitate these controls. The template case has only the stated single source-order cell; it does not establish template source-order invariance on its own.
